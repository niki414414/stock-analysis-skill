# Market Outlook 2.1

核心判断和固定输出格式见 `references/market-state-machine.md`。本技能负责取数、发现、
核验和编排；个股最终结论继续调用 `stock-analysis`，不得用行业强势替代个股分析。

## 核心原则

1. 价格结构只能说明“发生了什么”，不能自动说明“为什么”。
2. 行业相对强势只进入研究池，不构成买入信号。历史影子回测未支持机械追涨。
3. 非科技事件地图是已知线索库，不是完整事实库；无覆盖必须外部搜索补漏。
4. 日常价格简报可以把事件原因标为待核验，但不得因此编造原因；进入事件波段操作池时仍须通过资金、催化、公司质量、价格/盈亏比四道门。
5. 找不到可靠催化，或公司与题材关系无法核实，不得把代表股代理升级为事件波段候选。
6. 事件地图不是新闻归档终点。每个进入正文或交易观察池的催化都必须形成“首次提出—增量证据—市场首次响应—T+1/T+3/T+5/T+10/T+20—兑现或失效”的纵向档案；后续分析先查询旧档案，再搜索新增信息，禁止只搜最近新闻重写一遍故事。

## 催化生命周期记忆（强制）

解释板块产业原因、复核催化或进行事件波段研究前，先查询持久档案：

```bash
python3 "$TZ_CODEX_HOME/repo/skills/market-outlook/scripts/catalyst_dossier.py" search "关键词" --context --json
python3 "$TZ_CODEX_HOME/repo/skills/market-outlook/scripts/catalyst_dossier.py" show tech EVENT-ID
```

主题分析优先使用`search --context --json`一次召回相关事件、材料、早期信号、修正、前瞻、
公司关系、生命周期和价格响应，再由大模型按时间联系分析。它返回的是证据包和覆盖缺口，不是
机械热度或投资评分；共同出现事件不自动视为存在因果关系。`show`用于继续下钻单个事件。
查询词只出现在宽事件字段或材料正文时，输出必须区分`core_events`、`timeline`中的直接主题证据
与`parent_events`、`parent_context`中的上级背景；`company_mentions`只是材料文字点名，不能替代
`companies`中的结构化主题关系。`topic_status=uncovered`时直接报告未覆盖，不拼接相邻行业故事。

新增证据、里程碑、反证或推断时追加记录，不覆盖历史判断。`inference`必须明确标记，不能与
官方或公司一手证据混写：

```bash
python3 "$TZ_CODEX_HOME/repo/skills/market-outlook/scripts/catalyst_dossier.py" \
  record tech EVENT-ID --date 2026-08-31 --kind evidence --grade official \
  --summary "新增验证内容" --ref "来源URL"
```

催化首次提出、正式落地、证据升级和市场重新激活可以分别设为价格锚点。收盘后更新相关公司
相对沪深300的T+0/T+1/T+3/T+5/T+10/T+20响应，不得以单只龙头替代整个映射篮子：

```bash
python3 "$TZ_CODEX_HOME/repo/skills/market-outlook/scripts/catalyst_dossier.py" \
  track tech EVENT-ID --anchor-date 2026-08-28 --anchor-label "证据升级"
```

研究顺序固定为：先读历史档案与原始假设，再查目标窗口以来的增量信息，再看价格响应，最后
写支持、反证、确认和失效。近期新闻只能更新生命周期中的一个节点，不能替代更早的产业脉络。

### 与用户交互式维护

用户可以直接发送新闻、截图、博主材料、暗语释义或自己的观察，不要求使用固定模板。处理顺序：

1. 先用`search`和`show`查是否属于已有事件；不得看到新材料就另建一个重复事件。
2. 能明确归属时，追加为`evidence`、`milestone`、`invalidation`或`outcome`，并向用户返回一张简洁的“催化更新卡”：原逻辑、这次新增、证据等级、价格是否已先行、下一验证点、失效条件。
3. 暂时无法确认暗语、标的或事件归属时，先写入待归因队列，不丢弃，也不强行解释：

```bash
python3 "$TZ_CODEX_HOME/repo/skills/market-outlook/scripts/catalyst_dossier.py" \
  intake --date 2026-08-31 --summary "用户材料摘要" --grade user_material
python3 "$TZ_CODEX_HOME/repo/skills/market-outlook/scripts/catalyst_dossier.py" queue
```

4. 用户补充含义后，将待办关联到已有事件或标记为新事件，再按`update-event-map`流程正式入库。
5. 每次完整复盘只主动向用户询问最影响判断、且现有档案无法解决的1—3个问题；其余缺口留在队列，避免把交互变成填表。

固定交互输出不追求新闻罗列，而回答六个问题：它最早何时提出；这次究竟新增了什么；属于
事实、预期还是推断；产业链哪一环最直接；股价已交易到哪个阶段；接下来什么数据会确认或推翻。

## 工作流

### STEP 0：市场可执行简报（默认）

默认只运行输出驱动的新入口：

```bash
python3 "$TZ_CODEX_HOME/repo/skills/market-outlook/scripts/market_brief_v2.py" --save
```

它直接生成“正文＋实操问答＋证据展开”，不调用完整旧复盘、轮动雷达或事件库。默认覆盖
上证指数、创业板指、科创50和3—5个不同角色的申万一级板块，并为板块代理及当日容量代表股生成两级支撑、两级
压力、均线、启动量、分歧次数、持有/未持有观察任务、确认和失效条件。代表股仅是当日容量代理，
不自动等于产业核心或交易候选；未核验催化、公司和原策略身份前，代表股区间不能写成买卖指令。
用户点名板块时使用`--focus`；提供历史或自定义细分数据时使用`--input`。

交付顺序固定为：先在对话中完整展示本次V2正文，再给保存文件链接。展示时保留数据截止日、
上证指数、创业板指和科创50各自的箱体及确认/失效条件、3—5个板块的判断和观察区间、
明日执行条件与数据缺口；不得用摘要加Markdown链接代替完整展示，也不得漏掉新增的指数箱体。
只有用户明确要求简版时才缩写。`--save`仅负责留存，不改变对话交付顺序。

若异动原因不明，正文保留“待核验”并询问用户是否掌握新增线索，不为补齐叙事自动运行事件库。
只有用户明确要求解释产业原因、检查事件有效性、复核持仓或启动策略选股时，才进入后续专项流程。

### STEP 0.1：旧式全链路研究复盘（专项）

需要事件覆盖、持仓队列、策略路由或全景证据时调用旧编排器：

```bash
python3 "$TZ_CODEX_HOME/repo/skills/market-outlook/scripts/market_daily_review.py" \
  --top 10 --output-mode analysis --save-observation --json \
  > /tmp/market-daily-review.json
```

该脚本是现有工具的树干，不新增评分：内部依次调用 `market_state_fetcher.py` 和
`market_opportunity_radar.py`，统一输出数据日期、市场环境、指数技术区间、三张板块榜、核心/全景冲突、
外部篮子待核验项、策略启用建议、持仓复核队列和数据缺口。正式复盘优先读取这一证据包，
不再由模型临时拼接多个JSON。

若已有同一批次快照，可离线复用，避免重复取数：

```bash
python3 "$TZ_CODEX_HOME/repo/skills/market-outlook/scripts/market_daily_review.py" \
  --market-state /tmp/market-state.json \
  --radar /tmp/market-opportunity-radar.json --json
```

检查 `status`、`data_dates` 和 `checks.missing_required_sections`。`status=degraded` 时必须
说明缺失项；不得让大模型补造。`interpretation_contract` 是最终报告的强制边界。

框架升级后使用历史回放审计，不把它解释成选股策略收益：

```bash
python3 "$TZ_CODEX_HOME/repo/skills/market-outlook/scripts/market_framework_backtest.py" \
  --start 20260501 --end 20260817 --samples 8 --top 10 \
  --preheat-samples 3 --json
```

固定检查指数技术边界的5/10日触达与穿越、同花顺及申万二三级热点的1/3/5日相对表现、
预热状态后续表现、缺数情况和方法学限制。当前成分回放存在幸存者偏差时只能用于模块审计，
不得宣称预热策略已经获得收益验证。

### 两种输出模式（共用同一判断，不重复计算）

- 用户已启动“完整复盘”或“全景”，并要求“分析、为什么、详细讲讲”时，使用`--output-mode analysis`。保留研究和教学
  颗粒度：解释市场环境、重点方向证据、反证、确认与失效条件，但同一依据只讲一次；
- 用户说“决策版、今天怎么做、给我行动清单”时使用`--output-mode decision`。只展示一句
  市场姿态、最多3个关键方向、持仓动作、三类策略启停和关键条件；
- 两种模式必须读取同一证据包和同一判断，禁止为了让决策版更简洁而另算一套结论；
- 未说明时，“完整复盘”默认分析版；在分析版结尾附行动摘要，不另写一篇重复的决策报告。

正式复盘结束后固定询问用户当天实际决策。未回复只能记“决策未知”，不能自行推断为无操作。
统一复盘JSON先用`scripts/daily_decision_journal.py record-review`保存原始判断；用户回复后用
`record-decision`追加实际操作或“无操作”。到第3、5、10个交易日分别用`record-outcome`
追加结果，禁止修改原判断。预测对错、条件是否触发、用户是否执行和实际盈亏必须分栏评价。

账本已支持V2的`as_of_date / market / sectors`和完整原始快照；记录V2不需要手填交易日期。
旧离线包若个股复权口径不明，V2会保留指数与板块研究、暂缓个股买卖区间；应重取复权数据，
不得人工补一个复权标签绕过检查。到期自动结算与定时任务尚未实现。

完整复盘继续读取 `decision_routes`：

- `strategy_guidance` 只决定短线、催化波段、质量底仓的启用级别和关注方向；实际候选
  仍调用 `scripts/stock_strategy_router.py`，不得在复盘脚本中复制选股算法；
- `holding_review_queue` 从工作区 `holdings.csv` 召回非零持仓，逐项交给股票持仓模式或
  ETF/基金复核；大盘脚本不得直接生成个股买卖价；
- 持仓必须沿用 `strategy_identity`。身份缺失时先让用户归类，禁止短线被套后改成波段或底仓；
- 市场状态可以调整仓位倾向和策略启用级别，不能覆盖个股支撑、事件失效或原策略退出条件；
- 三种策略独立输出，禁止跨策略总排名。

用户问“完整复盘”时，默认只输出三块，后台证据不得全部倾倒给用户：

1. **盘面与板块**：一句市场状态，并对3—5个关键方向逐项展示全景篮子、产业核心、
   相对沪深300、扩散/活跃度、判断、风险、确认和失效条件；趋势榜与轮动榜必须分开，
   事件预热仅展示会改变下一步决策的方向。固定解读上证指数、创业板指、科创50的近期
   第一/第二支撑区、第一/第二压力区、向上/向下空间、近期实际5日波动和越界改判条件；
   第一路标用于观察反应，穿越后看第二路标，不得把它们包装成保证止跌/见顶的预测箱体；
   技术位不得只留在后台JSON；
2. **现有持仓**：每只只给策略身份、继续持有/减仓观察/触发退出等行动级结论，以及一个
   最关键条件；默认用表格展示数据日期、最新价、当日涨跌、成本盈亏、MA20/MA60位置、
   当前动作和下一步专项任务。基金无可识别代码时明确标注净值待复核；具体支撑位、估值、
   仓位比例和完整IF/THEN计划仅在用户点名后展开；
3. **下一步策略**：短线、波段、底仓分别标记“启动/选择性启动/暂停”，并明确本阶段
   主要采用哪一种。不给跨策略总排名。

默认只限制模块数量，不压缩板块分析的证据颗粒度。正文不重复无关脚本字段和完整后台
榜单，但重点板块必须达到“能看出为什么成立、哪里可能错、下一步看什么”的深度；不能只
用一两句话代替核心/全景数据。持仓和策略部分仍保持行动级简洁。
以下内容属于下一层，只有用户明确要求时才启动：

- 短线：运行活跃推土机，输出约20只候选、前5排序和图形教学；
- 波段：从趋势方向运行事件地图＋市场响应初筛，再进入六层；
- 底仓：运行独立质量与估值筛选；
- 单只持仓：股票、ETF或基金进入对应标的的六层复核，给具体价格和执行条件。

“完整复盘”本身不自动运行候选扫描器，也不逐股执行六层分析；复盘负责决定下一步启动
什么，不代替下一步工作。

python3 "$TZ_CODEX_HOME/repo/skills/stock-analysis/scripts/market_state_fetcher.py" \

### STEP 1：底层机会雷达（仅限内部调试或专项取数）

```bash
python3 "$TZ_CODEX_HOME/repo/skills/market-outlook/scripts/market_opportunity_radar.py" \
  --market-state /tmp/market-state.json --top 10 --json \
  > /tmp/market-opportunity-radar.json
```

该脚本：

- 用指数、广度、成交额识别异常结构；
- 扫描申万一级行业相对沪深300的当日/5日/20日强弱；
- 另以同花顺概念热度和申万二/三级行业补足细分轮动发现；同花顺标签只代表市场热度，
  不代表公司主营纯度，也不得直接升级为个股推荐；
- 用申万成分股聚合5日 Tushare `moneyflow`，计算资金连续性；
- 将行业上涨家数与全市场上涨比例比较，避免普涨日候选泛滥；
- 直接调用非科技事件地图 `window`，不依赖当前缺失的 `sectors_status` 表；
- 将沪深300质量池作为 `quality_core` 标签接入，不把质量等同买点；
- 合并 `quality_core`、`catalyst`、`market_response` 三种独立候选来源；
- 公司—事件正式关系默认从SQLite读取；Excel只作为显式双读或紧急回退；
- 将方向分为 `active_catalyst_found` 与
  `coverage_gap_requires_external_search`；
- 输出待核验公司和外部搜索词，但不输出买入信号。

正式板块判断优先读取 `market_environment` 和 `sector_views`，禁止把不同时间尺度
混成一个“板块最强榜”：

- `sector_views.trend_watch`：服务波段观察，只回答持续性，不直接产生买点；
- `sector_views.rotation_watch`：服务短线观察，只回答当日攻击和扩散，不得写成未来一周趋势；
- `sector_views.event_preheat_watch`：服务左侧跟踪，价格和扩散确认前不得升级；
- `sector_views.hotspot_discovery.rotation_spine`：申万二/三级是正式轮动骨架；
- `sector_views.hotspot_discovery.supplemental_concepts`：同花顺仅补充申万未表达的新概念，
  重合项挂到申万方向的`ths_context`，不重复占用报告名额；
- `sector_opportunity_map` 仅为兼容和证据明细输出，不得按其顺序声称趋势强弱；
- 细分篮子 `n_stocks<5` 必须写明“低覆盖、仅代表核心样本”；5—7只为有限覆盖；
- 趋势榜必须同时展示5日、20日、相对沪深300、篮子中位数和5日上涨比例；
- 若中位数或上涨比例缺失，只能写“持续性线索”，不能写“板块趋势已确认”。

`market_environment` 必须先于板块榜解读。普涨环境下，单日绝对上涨比例解释力下降，
必须使用相对全市场广度；缩量普涨不得自动视为增量行情。

`sector_views.event_preheat_watch` 同时接收事件先行和盘面先行两条召回路径。盘面先行
证据由共享 `skills/shared/sector_preheat.py` 计算，固定观察相对抗跌、3日相对强度
加速度、广度低位改善、核心梯队和日线量价承接。出现2项为早期改善、3项及以上为资金
试探；它们只决定次日观察顺序。没有有效催化的盘面先行方向必须先反查事件，不能直接
进入催化波段候选。该层不使用MACD底背离，也不把日线代理解释为真实机构订单流。

细分篮子采用双输入，但两类数据不得互相覆盖：

- 产业输入：最新科技事件 `sectors_status.signal_stock_code`，输出到
  `event_core`，回答产业材料当前覆盖哪些代表公司；
- 外部输入：`config/subsector_basket_supplement.csv`，只允许来源可追溯且
  `review_status=approved`、未过期的记录进入 `market_panorama`；
- `candidate`、`rejected`、已过期和格式错误记录只能进入
  `external_review_queue`，不得参与收益、广度或趋势计算；
- 外部补充不得反写事件地图，不得把官方指数成分自动解释为主营纯正；
- `business_relevance=medium/low` 的股票只能承担市场表征，进入个股推荐前仍需六层分析；
- `active_response` 由全景篮子内当日涨幅、5日涨幅或成交活跃度动态发现，服务短线，
  不得自动升级为产业核心。

每个篮子同时比较 `event_core` 与 `market_panorama`：核心强而全景弱是龙头行情；
全景活跃而核心弱偏概念轮动；两者同时走强才提高板块趋势置信度。外部登记表至少
每月复核一次，指数调样、基金定期报告更新或 `valid_until` 到期时必须重新核验。

### 细分篮子维护频率与简化边界

日常运行不得重新全网搜索和重建篮子。固定执行频率如下：

- 每个交易日收盘：只读取已核验成分，批量计算主题代理、全景篮子、产业核心和
  `active_response`；不做全量成分搜索；
- 每月一次：集中复核外部登记表，检查官方指数调样、ETF最新定期持仓、公司业务变化、
  过期记录和样本代表性；成熟方向允许在数据无变化时沿用至下一月；
- 两个月上限：成熟板块最迟两个月必须完成一次复核；机器人、商业航天等高变化主题
  仍按每月复核；
- 临时触发：只有出现官方调样、重大产业事件、新主线、篮子与盘面明显背离、篮子外
  新龙头或公司重大基本面变化时，才在月度周期外补录；
- 搜索发现的新公司默认写为 `candidate`，核验来源和业务相关度后才能改为 `approved`。

每个重点方向采用最小可用结构：一个主题指数或ETF代理、8—15只全景观察股、3—5只
产业核心股；不得为了覆盖面无限扩充。日常趋势判断固定只看四项：

1. 主题指数或ETF的5日相对强弱；
2. 全景篮子5日收益中位数；
3. 全景篮子5日上涨比例；
4. 产业核心篮子是否同步。

四项足以回答日常方向时，不再增加指标或临时评分。指数、全景、核心同时强才提高趋势
置信度；指数强而全景弱视为权重行情；全景强而核心弱视为概念轮动；事件强但价格未响应
视为预热。成交活跃度、创新高家数等只作为出现分歧时的二次诊断，不作为日常强制层级。

随后读取 `sector_opportunity_map` 的证据明细：

- `evidence_cluster`：相对强度、相对市场广度、持续资金、有效催化中至少三项
  聚集，且必须同时通过相对强度和持续资金；
- `research_candidate`：有两项证据，但尚不足以称机会聚集；
- `weak_or_unconfirmed`：只有一项或没有有效证据；
- `candidates[].tags`：`quality_core`、`catalyst`、`market_response`；
- 只有两个及以上独立标签的公司才标为 `six_layer_priority`，单标签只能观察；
- `opportunity_snapshot_meta.moneyflow` 必须检查 `latest_trade_date` 和 `lagged`。
  资金数据未发布时保持不可用，不能填0，也不能换免费源。

`advance_ratio` 只描述行业内部上涨比例；正式判断使用
`advance_excess_vs_market`。普涨修复日不得把绝对高广度当成板块独立走强证据。

### STEP 2：异常波动原因核验

若 `abnormal_structure.triggered=true`，必须执行联网搜索。优先使用脚本给出的
`cause_search_queries`，并补查：

- 宏观/政策：央行、监管、权威媒体；
- 外盘/跨资产：海外指数、利率、汇率、商品；
- 产业：行业政策、价格、订单、供需；
- 公司：公告、业绩、减持、监管；
- 交易结构：ETF申赎、两融、成交额、拥挤和技术破位。

输出必须分开：

1. **结构诊断**：由行情数据直接支持；
2. **主要原因**：至少一条可靠、时点吻合的外部证据；
3. **次要原因**：有证据但解释力较弱；
4. **已排除说法**：时点或数据不吻合；
5. **置信度与待确认项**。

不得把搜索结果的标题、市场传言或价格反推当成已证实原因。

### STEP 3：非科技轮动二次核验

逐一处理雷达方向：

- `active_catalyst_found`：联网核实事件是否真实、仍在有效期、当天是否新增；
- `coverage_gap_requires_external_search`：搜索政策、订单、涨价、业绩和供需变化；
- `sector_opportunity_map` 中板块成立但没有双标签公司：明确输出“板块成立、公司待发现”，
  不得因为质量池或事件公司池为空而静默跳过；
- 只有单日防守性上涨、无新增催化：标为“资金避险候选”，不称新主线；
- 有催化但没有板块扩散：标为“题材试探”；
- 有资金持续性、有效催化、板块扩散：才标为“轮动候选”；
- 对公司候选调用 `stock-analysis`，核实主营相关度、业绩质量、估值、趋势和风险。

公司关联为 `event_text_fallback` 或 `event_text_code_map_only` 时，必须查公告或公司业务
资料确认，不能直接采用。

SQLite返回的`benefit_tier=主题观察`同样只作低层级召回，不得跳过六层第三层的主营和
业务占比核验。

### STEP 4.5：战略方向哨兵（强制扫描、条件展示）

读取 `config/strategic_theme_watchlist.csv`，后台扫描：

- 机器人；
- 商业航天；
- 脑机接口；
- 工业母机；
- 六张网与新兴支柱产业；
- 科技基础设施；
- 国产替代与自主可控。

这些方向横跨机械、汽车、电子、计算机、通信、军工、医药等多个申万一级行业，
不得用一级行业涨跌或 `sector_opportunity_map` 是否入榜作为不扫描的理由。扫描时检查：

1. 细分篮子当日/5日/20日价格强弱（无篮子时明确标注覆盖缺口）；
2. 板块广度和资金持续性；
3. `window` 中仍有效的催化及可信度；
4. 当前处于超跌反弹、新主线试探、预热、强化、分歧或退潮；
5. 从政策/技术叙事升级为产业事实所需的订单、项目、认证、产能、收入或利润指标。

仅在以下情况进入报告正文：资金、广度、有效催化三项中至少两项成立，或出现足以改变
市场/行业判断的政策、订单、临床、技术或量产节点。其余方向不逐项展开，统一用一句
“其余战略方向未触发”收束；详细数据留在事件地图和观察池。

若行情数据和事件数据结论冲突，触发方向必须同时保留两类证据，不得用其中一项覆盖另一项。例如：
“商业航天有发射催化但资金未确认”“机器人一级机械行业偏弱但核心零部件已出现5日持续性”。

### STEP 5：组装报告

完整读取 `references/market-state-machine.md` 作为后台判断依据，但默认报告必须压缩成：

- 盘面与板块：市场状态、3—5个关键方向的完整核心/全景证据、轮动榜及未来1—5日触发器；
- 现有持仓：行动级摘要；
- 下一步策略：短线/波段/底仓启用建议及首选策略。

异常原因、三榜明细、非科技证据、科技主线、战略哨兵和数据缺口只在它们会改变上述三项
决策时进入正文；其余保留在标准证据包中。若用户要求选股，再调用统一策略路由器。

每个重点方向必须附四项：支持证据、不足或反证、确认条件、失效条件。不得只输出
单向预测。报告中“未来一周较强”只能来自趋势榜；轮动榜只能使用“当日攻击、次日观察”
等表述；事件预热榜只能使用“等待市场确认”。

## 降级处理

- 单个数据源失败：标明不可用，继续用其余证据，不补造数字。
- 行情与资金日期不同：分别标注 `price_date`、`moneyflow_date`；不得默认同日。
- 非科技状态表缺失：属已知限制，雷达不调用 `status --source nonfin`。
- 事件地图无覆盖：生成外部搜索队列；搜索仍无可靠证据则不操作。
- 联网搜索不可用：只给结构诊断和待核验清单，不给确定性原因或机会结论。
