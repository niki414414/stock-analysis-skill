# 工具迭代必须以真实任务结果为中心（2026-09-08）

## 背景

过去约一个月，股票工具尤其是事件库反复经历“发现使用效果不好→增加字段、脚本、入口或设想
新的自动化链路→仍然没有得到需要的分析结果”。2026-09-08以MLCC为真实案例复核后确认：
事件库已经保存了事件、材料、早期信号、修正、前瞻和公司关系，足以还原从涨价预期、供给
收缩、长协到业绩验证的连续脉络。此前没有连续分析，主要原因不是库里没数据，而是使用时只
查最新记录、没有召回全历史并做联系、比较和推理。

## 根因

1. 把用户需要的“分析结果”误解为需要建设更完整的“系统”。
2. 没有先用真实案例运行现有正式入口，就依据想象设计改造。
3. 把“数据已经存在但没有被分析”误判成“数据结构不足”。
4. 把金十、公众号、MLCC、热度和资金等例子逐个转化为模块需求，围绕局部例子见子打子，
   没有持续回到“结合历史上下文形成投资研究参考”的上位目标。
5. 混淆信息进入、连续研究和交易决策三个不同问题，试图一次性建立全自动闭环。
6. 没有先核对现实能力边界，提出了无法稳定实现的公众号自动读取、持续资金监控和主动到期
   提醒。按需查询只能形成带时间戳的快照，不能表述为监控。
7. 高估增加代码和结构的价值，低估完整召回、时间排序、正反证比较和语义综合的重要性。
8. 缺少改动前后的同案例验收，所以“代码完成”长期替代了“用户结果改善”。

## MLCC案例为什么部分有效

本次没有先修改工具，而是直接：

1. 同时查询`events`、`early_signals`、`materials`、`corrections`、`forward`、赛道状态和公司关系；
2. 按日期还原“AI高容需求→现货涨价→供给与转产→直接客户涨价→长协→利润验证”；
3. 将核心产业方向与50%—150%涨幅、30%配额等低等级精确说法分开评价；
4. 同时呈现降价、价格暴跌传闻及数据库中的反驳和保留意见；
5. 把热度限定为库内记录密度和当时保存的赛道状态，不冒充2026-09-08实时市场热度；
6. 明确指出MLCC没有生命周期观察和价格响应快照、部分公司映射过宽、最新增量停在8月中旬。

它证明现有事件库能够支持历史连续性研究，主要缺口是固定的分析调用顺序。它尚未证明对一条
今天新增的材料能完成“本次增量＋当前外部验证”，后者应以真实新材料另做验收，不能从本案例
外推为已经完成。

## 今后所有工具修改的强制顺序

```text
写清用户结果和非目标
→ 选择一个真实验收案例
→ 完整运行现有正式入口
→ 展示现状结果和数据边界
→ 将缺口归类
→ 只修最小缺口
→ 用同一案例复验前后差异
→ 有效后才写入正式规则
```

缺口分类只能优先落入以下一种：

- 数据确实缺失；
- 数据存在但未被召回；
- 数据已召回但缺少联系、比较和推理；
- 计算或判断逻辑错误；
- 正确结果没有进入正式消费输出。

如果属于第二或第三类，先修查询顺序、分析指令和输出规范，不新增数据库、脚本、评分器或入口。

## 停止条件

出现以下任一情况，必须停止扩张方案并回到真实案例：

- 还没有运行现有工具，就开始设计新架构；
- 用“可能、应该、以后也许需要”替代当前失败证据；
- 因用户举了一个信源或行业例子就新增专用模块；
- 把按需数据说成持续监控，把可打开单篇链接说成可以自动追踪平台；
- 为了显得完整，一次性连接事件、选股、六层、资金、提醒和交易；
- 修改后只能证明代码运行，不能说明用户得到的结果改善在哪里。

## 不同工具的适用方式

- 事件库、文章校验、六层解释：优先检验完整召回和语义综合，很多问题不需要改代码。
- 推土机、波段、评分和排序：同样先跑真实案例，但修改规则还必须经过历史或连续样本验证，
  不能因为单例解释更顺就调整分数。
- V2箱体复盘：只围绕箱体、板块结构和操作区间验收，不因案例涉及涨停或事件就扩大边界。
- 数据与基础设施：只有真实消费者读到陈旧、冲突或错误数据时才改；修复后必须由消费者复验。

## 对既有改造的判断

SQLite统一主库、旧CSV退出默认消费、公司关系统一，以及正式更新时保留生命周期增量，解决了
真实的数据一致性和未来记忆问题，应保留。没有落地的固定10条样本、全市场自动雷达、公众号
自动抓取、持续资金监控和复杂事件状态机，不再作为当前任务方向。

长期原则：先把现有工具用对，再判断是否需要把工具做大。
